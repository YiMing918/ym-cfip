多源聚合的 Cloudflare 优选 IP 站：**全球 1000+ 条、66+ 个地区**，地区/运营商/数量/延迟/速度全都能自己选，浏览器本地实测可用性，一键生成可**自动更新的订阅链接**。纯静态 + Pages Functions，免费额度内运行，GitHub Actions 定时聚合数据。

> 本站只聚合公开优选源并做格式整理，**本身不测速**：每条数据的延迟/速度来自其源站在测试地的实测（页面与数据文件均标注来源与口径）。「本地可用 / 本地测速」是访客浏览器在**访客自己网络**上的现场探测。

## 功能亮点

**数据聚合**
- 19 个数据源条目自动聚合去重：单地区实测源（svip-s）、微测 WeTest、CFYes、麒麟 UOUIN、CM 优选、辣椒、洛璃、Mia、天诚、vvHan、NiREvil 等
- 全部统一为 `IP:端口#地区 [类型]` 格式；无地区标注的条目一律不收，宁缺毋滥
- 独立 **IPv6 池**（源不带地区标注，单独成池）与 **优选域名**列表（含运营商分流域名）

**自选生成**
- 地区墙：66+ 个地区带实时条数，点选/多选，快捷预设（美日 / 亚洲 / 欧洲 / 美洲 / 全选）
- 运营商四网多选：移动 / 电信 / 联通 / 广电任意组合（带标注条数实时显示）
- 数量自己定：统一「每地区最多 N 个」，或给每个地区**单独定数量**
- 门槛自己定：最大延迟、最低速度、端口（全部 / 仅 443 / TLS 常用）、取数方式（质量优先 / 随机抽取）
- 整套选项可存成**分享链接**，打开自动恢复

**本地检测（访客浏览器内运行）**
- 「检测本地可用」：全池逐个试连，或只检测已选地区；地区钮上标出 ✓可用数，一键「只选有可用的地区」
- 清单「本地测速」：双测取低值，可按延迟排序；生成时可勾「只生成本地测通的」
- ⑥ 大池采样：从 Cloudflare 官方 IP 段（约 190 万地址）随机采样 500–5000 条（标注未实测），本地检测后只复制可用的
- 导出格式自定义：备注名用模板拼（地区 / 代码 / 序号 / 延迟 / 网速 / 运营商 / 来源 / 端口 / 日期 / 标签 / 旗帜，共 11 个变量），6 个预设一键套用，想加啥加啥；套用到复制、下载与订阅链接（`fmt` 参数），导出自动按地区重编序号（`#JP1`）
- 访客属地识别条：三路接口兜底，显示访客出口省市与运营商，并提示与数据源地的关系
- 优选域名批量实测：逐个测真实延迟与落地机房（trace 法）

**订阅与导出**
- `/sub` 动态端点：把页面选项拼进链接，客户端每次拉取都按**最新数据**现算清单
- **快照订阅**：把当前清单（含本地测通筛选与导出格式）一键存成专属链接 `/s/<id>`（Cloudflare KV 定格存储，保留 180 天）— 本地测速结果从此也能进订阅；快照不随聚合变化，重新测速后再存一次生成新链接
- 链接可带建议更新间隔；每个分组与 Top 20 都有固定直链（.txt），可直接当订阅源
- 复制 / 下载 .txt / 送外部复检站（推荐 IPCheck.ing，可自填任意监测站）

**今日推荐**
- 高速优选源按测速排名的 Top 20，支持复制 / 下载文件 / 复制直链

## 快速部署

1. **Fork 或克隆本仓库**到你的 GitHub 账号。

![部署第1步](https://gcore.jsdelivr.net/gh/YiMing918/ym-cfip@main/docs/deploy-step1.png)

2. **连接 Cloudflare Pages**：Cloudflare 控制台 → Workers 和 Pages → 创建 → Pages → 连接到 Git，选择本仓库。构建设置：框架预设「无」、构建命令留空、输出目录 `/`，生产分支 `main`。保存并部署。

![部署第2步](https://gcore.jsdelivr.net/gh/YiMing918/ym-cfip@main/docs/deploy-step2.png)

3. **（可选）绑定自定义域名**：Pages 项目 → 自定义域 → 添加你的域名。
4. **开启自动更新**：仓库 Actions 页确认 `聚合优选 IP 数据` 工作流已启用（Fork 的仓库需手动启用一次 Actions）。
5. **（可选）开启快照订阅**：Cloudflare 控制台 → KV 建一个命名空间 → Pages 项目 → 设置 → 绑定，添加 KV 命名空间绑定，变量名 `SNAP`。不绑也不影响其他功能（点存快照时会提示未配置）。

![部署第3步](https://gcore.jsdelivr.net/gh/YiMing918/ym-cfip@main/docs/deploy-step3.png)

部署完成后：
- 站点首页即优选清单工具；`/sub?...` 订阅端点由 `functions/sub.js` 提供，Pages 自动生效，无需额外配置。
- 想改聚合频率：编辑 `.github/workflows/update.yml` 的 cron（默认每 2 小时，`20 */2 * * *`）。

## 订阅端点 /sub

把选项写进链接，客户端拉取时现算。示例：

```
/sub?regions=JP,US&n=20&ms=200&ui=12
```

| 参数 | 说明 |
|---|---|
| `regions` | 地区代码逗号分隔，缺省 `JP,US` |
| `n` | 每个地区最多 N 个 |
| `rn` | 单独定量，如 `rn=JP.10,US.5`（覆盖 `n`） |
| `ms` | 最大延迟 ms（按源标注延迟） |
| `mbps` | 最低速度 Mbps（按源标注速度） |
| `carrier` | 运营商可多选（逗号分隔，如 `移动,电信`）：带标注的只留所选，无标注源保留 |
| `ports` | `443` 或 `tls`（443/8443/2053/2083/2087/2096），缺省全部 |
| `mode` | `random` 随机抽取，缺省质量优先（源序） |
| `stack` | `stack=6` 输出 IPv6 池（此时 regions/ms/mbps 不适用，可用 `n` / `carrier`） |
| `ui` | 建议客户端更新间隔（小时），写入 `profile-update-interval` 响应头 |
| `fmt` | 导出格式模板（URL 编码），变量 `{地区} {代码} {序号} {延迟} {网速} {运营商} {来源} {端口} {日期} {标签} {旗帜}` 自由组合；缺省为 `#代码序号 [原始标签]` |

页面上的「我的订阅链接」卡会随选项自动拼好这条链接，复制即用。

## 自动更新（总池为什么是活数）

- GitHub Actions 默认**每 2 小时**运行 `scripts/aggregate.py`：抓取全部源 → 解析（原生格式源直接收录；混杂格式源提取地区代码，识别不了一律剔除）→ 去重 → 生成 `data/*.txt` 与 `data/meta.json`，有变化才提交，Pages 随之自动重新部署。
- **每轮从零重建、不是往旧池子上叠加**：源增它增、源减它减，同一 IP 被多个源收录只算一次（按来源优先级归属）。所以总池数字每轮都会小幅浮动，这是正常现象，不是统计错误。
- **改频率**：编辑 `.github/workflows/update.yml` 的 cron 一行即可（默认 `20 */2 * * *` = 每 2 小时；GitHub 定时任务最密 5 分钟一次）。这是部署者自己的设置，每份部署互不影响。
- `data/history.json` 保留最近 30 次聚合的条数记录，页面底部可查。
- 静态种子数据 `seed-usjp.txt`（美日精选）不随源更新，可自行编辑增删。

## 数量与拉取方法（为什么每个地区只有几十到几百条）

先给数字：总池约 1000 条、66 个地区，其中美国约 340、日本约 110、新加坡约 70、香港约 60，往后多数地区只有几到几十条，小地区可能只有 1–2 条。别家动辄「每地区几千条」，差别来自**拉取方法**，不是谁漏抓了：

**本站的方法：只收别人实测后发布的成品清单，再严过滤。**
1. **不自己扫网段**：19 个源都是维护者在各自网络里实测后发布的优选清单，单个源本来就只有几十到几百条。本站只拉取、解析、合并，不对 Cloudflare 官方网段做扫描。
2. **无地区标注一律剔除**：混杂格式的源必须能识别出地区代码才收（识别不了直接丢），宁缺毋滥 — 这一刀就砍掉不少。
3. **按「IP:端口」全网去重**：同一个 IP 被 5 个源同时收录，在总池里只算 1 条（按来源优先级归属）；同 IP 的重复条目不重复计数。
4. **每轮从零重建**：不攒历史库存，源站剔除的失效条目本站同步消失。

**别家「几千条一个地区」通常是另一种做法：**
- **扫描型**：拿官方 CIDR 段（约 190 万地址）批量扫，产出的是「扫到的地址」而非「测好的优选」，绝大多数没测过速度、很多是死的 — 本站把这种数据单独放在 ⑥「大池采样」里并标注未实测，不混进主池充数。
- **采集型**：把几十个源无差别堆叠，不验地区、不去重、失效不删，数字大但水分大。

**取舍很明确**：本站主池走「条条有出处、有地区、去过重」的口径，数量自然小一个量级；想要量，用 ⑥ 大池采样（官方段随机采样 + 本地检测自己筛）。地区分布则由源决定 — 源多从国内测美/日/新/港，小地区只有零星覆盖，这是全行业的共同现状。

## 口径与边界

- **标注数据不是你的实测**：延迟/速度是源在其测试地的成绩。离测试地越近参考价值越高；你本地的真实表现以「检测本地可用 / 本地测速」和本地 CloudflareSpeedTest 为准。
- **「本地可用」定义**：浏览器向 IP 发起 HTTPS 握手，超时内有响应即记可用（证书不匹配 IP 会报错返回，测的是报错前耗时）。可用 ≠ 节点能用或速度达标。开着代理时测的是经代理的连通性。
- **广电**：全网暂无公开的广电实测优选源。选广电时返回通用条目并给出提示 — 广电用户请用本地检测在自家网络实测筛选。
- **实时订阅不含本地可用**：本地检测只存在于访客浏览器，服务端无法复现，故 `/sub` 只接受地区/数量/门槛/运营商/端口/格式参数。要把本地测通结果变成订阅，用③卡的**快照订阅**：把当前清单定格存进 KV，链接内容就是你测过的那批。
- **探测超时统一 5 秒**：全池检测、清单测速、IPv6 与大池探测都用 5s（对齐 Mihomo/Clash 健康检查的业界默认），避免同一条目在这处通、在那处超时。
- **计数对得上账**：检测数与生成数不一致通常是运营商/门槛过滤在起作用（检测不分运营商、生成会过滤），页面会把被滤掉的条数明确标注；导出默认按地区分组编号（日本 1..N 完再到美国），与 `/sub` 口径一致。
- **优选域名**由第三方维护，使用人数多时晚高峰可能变卡，适合作回退入口。

## 常见问题

**Q：为什么某个源显示「已聚合 0 条」？**
A：该源当轮条目与别的源重复、或没有可识别的地区标注（按「宁缺毋滥」规则剔除），没有净增条目，属正常现象，不代表源挂了。

**Q：总池条数为什么每轮都不一样？**
A：每轮聚合都把全部源重新抓一遍、从零重建：源增它增、源减它减、重复只算一次。浮动是个位数到几十条的正常呼吸，页面顶部「更新于」是最近一轮的时间。

**Q：检测了 301 个，生成清单只有 295 个，差在哪？**
A：检测只看通不通、不分运营商；生成时会执行运营商/延迟/速度/端口过滤。多半是运营商筛选滤掉了别家运营商的标注条目 — 页面计数旁会标注「运营商筛选滤掉 N 条」，对得上账。

**Q：为什么每个地区条数比别家少那么多？**
A：拉取方法不同。本站只收各源实测发布的成品清单，且无地区标注剔除、按 IP:端口 全网去重、每轮重建不攒库存；别家的「几千条」多是扫描官方网段的未实测地址或未去重的采集堆叠。详见上方「数量与拉取方法」一节；想要量可用页面 ⑥「大池采样」。

**Q：聚合频率能改吗？**
A：能。改 `.github/workflows/update.yml` 里 cron 一行（默认每 2 小时）。注意它和页面上「客户端更新间隔」是两回事：后者只是写给客户端的拉取建议（`ui` 参数），不改变后台聚合节奏。

**Q：订阅链接里的内容多久变一次？**
A：链接本身实时现算，内容取决于数据新鲜度：聚合每 2 小时更新一次（可改），客户端按 `ui` 建议间隔或其自身设置拉取。

**Q：部署后 Actions 不跑？**
A：Fork 的仓库默认禁用 Actions，到仓库 Actions 页手动启用；另外定时任务在 GitHub 免费版偶有延迟，属正常。

**Q：可以加自己的源或自己的 IP 吗？**
A：可以。编辑 `seed-usjp.txt` 加静态条目；或改 `scripts/aggregate.py` 的源列表加新源（需能解析出地区）。

**Q：新 Cloudflare 账号点「连接 GitHub」一直跳回应用设置页，看不到仓库？**
A：GitHub 上的「Cloudflare Workers and Pages」应用只能绑定一个 Cloudflare 账号。若你的 GitHub 已绑过另一个 CF 账号，新账号就连不上（卸载重装会断开旧账号项目的 Git 部署，慎重）。解法：新账号改用「直接上传」建 Pages 项目，再到新账号创建一个 Pages 编辑权限的 API 令牌，与账号 ID 一起存入仓库 Secrets（`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`），本仓工作流会在每次聚合后自动把最新站点推送部署上去，效果与连 Git 一致。

**Q：Fork 后工作流里「推送部署」那步需要我处理吗？**
A：不需要。没配上述两个 Secrets 时该步自动跳过，聚合与数据提交照常；连 Git 部署的用户本来也用不到它。
