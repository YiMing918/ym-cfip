# YM 优选 IP · Cloudflare 全球优选清单站

## 功能亮点

**数据聚合**
- 38 个数据源条目自动聚合去重（27 个 IP 源 + 1 个静态种子 + 10 个域名源）：单地区实测源（svip-s）、微测 WeTest、CFYes、麒麟 UOUIN、CM 优选、辣椒、洛璃、Mia、天诚、vvHan、NiREvil、S5 公益、Joname、辣子鸡、Kristi、MJZ、love-ztm、yuanxiawan、ahang39 等；域名源为 svip-s、BestCF（全量 / 亚洲 / 高访问量 / 甬哥 / 秋名山 / Senflare / IRCF）、cf-nodes、cmliu 官方
- 全部统一为 `IP:端口#地区 [类型]` 格式；无地区标注的条目一律不收，宁缺毋滥
- 独立 **IPv6 池**（源不带地区标注，单独成池）与 **优选域名**池（10 源聚合去重 800+ 个，聚合时 DNS 解析筛除失效域名，每行备注带出处；另含社区运营商分流域名）；两张卡都有与 IPv4 清单同规格的构成统计与实测汇总

**自选生成**
- 地区墙：60+ 个地区带实时条数，点选/多选，快捷预设（美日 / 亚洲 / 欧洲 / 美洲 / 全选）；另含「三网专区」— 无地区、只有运营商实测的破例收录区
- 运营商四网多选：移动 / 电信 / 联通 / 广电任意组合（带标注条数实时显示）
- 数量自己定：统一「每地区最多 N 个」，或给每个地区**单独定数量**
- 门槛自己定：最大延迟、最低速度、端口（全部 / 仅 443 / TLS 常用）、取数方式（质量优先 / 随机抽取）
- 整套选项可存成**分享链接**，打开自动恢复

**本地检测（访客浏览器内运行）**
- 「检测本地可用」：全池逐个试连，或只检测已选地区；地区钮上标出 ✓可用数，一键「只选有可用的地区」
- 清单「本地测速」：双测取低值，可按延迟排序；生成时可勾「只生成本地测通的」
- ⑥ 大池采样：从 Cloudflare 官方 IP 段（约 150 万地址）随机采样（预设档 500–5000，自定义 100–10000，标注未实测），本地检测后自动识别可用条目的**真实落地地区**（trace 读取），可按地区筛选、只复制可用的，还能把这批存成**快照订阅**；卡上标注每次采样的生成时间与当前检测网络。注意：裸地址采样阶段没有地区/运营商数据，地区是检测后按落地识别的 — 这是 Anycast（任播：同一 IP 在全球多机房应答）的事实，声称能「按地区采样」的都是编的
- 导出格式自定义：备注名用模板拼（地区 / 代码 / 序号 / 延迟 / 网速 / 运营商 / 来源 / 端口 / 日期 / 标签 / 旗帜，共 11 个变量），6 个预设一键套用，想加啥加啥；套用到复制、下载与订阅链接（`fmt` 参数），导出自动按地区重编序号（`#JP1`）
- 访客属地识别条：三路接口兜底，显示访客出口省市与运营商，并提示与数据源地的关系
- 优选域名批量实测：逐个测真实延迟与落地机房（trace 法：Cloudflare 的机房信息接口）

**订阅与导出**
- `/sub` 动态端点：把页面选项拼进链接，客户端每次拉取都按**最新数据**现算清单
- **快照订阅**：把当前清单（含本地测通筛选与导出格式）一键存成专属链接 `/s/<id>`（Cloudflare KV 定格存储，保留 180 天）— 本地测速结果从此也能进订阅；快照不随聚合变化，重新测速后再存一次生成新链接
- 链接可带建议更新间隔；每个分组与 Top 20（前 20 名）都有固定直链（.txt），可直接当订阅源
- 「各源原始直链」卡：38 个来源里除静态种子外的 37 条源站原始链接照原样列出（附各自更新节奏与复制按钮），访客可绕开本站聚合、直接用任意一家的原味订阅 — 内容由源站自己更新，客户端每次拉取都是源站最新版，本站只列地址、不过手数据
- 复制 / 下载 .txt / 送外部复检站（推荐 IPCheck.ing，可自填任意监测站）

**今日推荐**
- 高速优选源按测速排名的 Top 20（前 20 名），支持复制 / 下载文件 / 复制直链

**界面**
- 分类类目导航：顶部 9 个类目点哪个只显示哪个（今日推荐 / 选 IP / 订阅 / 域名 / IPv6 / 大池 / 直链 / 来源 / 说明），告别长页滚动，手机上尤其清爽；默认落地「今日推荐」；带卡片锚点的链接打开自动切到对应类目
- 站内「说明」类目内置图文版使用说明（四步上手），第一次来的人不用猜

## 使用说明

页面顶部是**分类类目导航**：点哪个类目就只显示哪个类目的内容，不用从头翻到尾。第一次用，按四步走：

**第一步 · 选** — 在「①② 选 IP」里勾地区、定每地区数量（每个地区还能单独改数量），按需多选运营商（移动 / 电信 / 联通 / 广电）、设延迟与速度门槛，点「生成清单」。计数旁会标注被运营商 / 门槛滤掉的条数，账算得清清楚楚。

![清单](https://gcore.jsdelivr.net/gh/YiMing918/ym-cfip@main/docs/preview-list.png)

**第二步 · 验** — 对清单点「本地可用检测」或「本地测速」。这是在**你自己的浏览器、你当前的网络**上现场探测（超时统一 5 秒）：本站给的延迟 / 速度是各源站在自家测试地测的，只作参考；你测出来的才是对你有效的。测完有分地区「共 N 条 · 通 M 条」统计。

**第三步 · 用** — 直接复制清单粘进客户端；或者在「③ 订阅」里把当前清单存成**快照**，生成专属 `/s/<id>` 链接：只含本地测通的 / 只含测速 ≤ 你设的阈值的 / 全部，三档自选，成果定格、不随聚合变动。

![订阅](https://gcore.jsdelivr.net/gh/YiMing918/ym-cfip@main/docs/preview-sub.png)

**第四步 · 长效** — 想让客户端自己定时换新：用「③ 订阅」的 `/sub` 实时订阅链接（随本站每轮聚合自动更新，参数就是你页面上的选择），或去「直链」拿现成分组 `.txt`；想用某家原味订阅的，「直链」里还有 37 条**各源原始直链**，内容由源站自己更新。

其余类目：**今日推荐**是高速源测速 Top 20（前 20 名），现成可用；**域名 / IPv6 / 大池**是三个独立池子（大池是官方段随机采样，抽到的地址没测过，靠本地检测 + 落地地区识别筛）；**来源**列每个源的聚合条数与更新记录；**说明**是站内版使用说明与全部口径。更细的规则见下方[口径与边界](#口径与边界)与[常见问题](#常见问题)。


## 新手先看这里：部署要先准备什么

完全没用过 Cloudflare / GitHub 也没关系，先把下面四样东西准备好，每一样都写清了「是什么、去哪弄、多少钱」：

1. **GitHub 账号**——代码托管网站，本项目的代码就放在这里，自动更新也靠它。去 [github.com](https://github.com) 点右上角 **Sign up（注册）**，用邮箱注册，**免费**。
2. **Cloudflare 账号**——站点就跑在它家的免费托管（Pages，读作「佩奇斯」，就是 Cloudflare 提供的免费网站托管服务）上。去 [dash.cloudflare.com](https://dash.cloudflare.com) 点 **Sign up（注册）**，用邮箱注册，选**免费计划（Free）**就够本站用，**0 元，不需要服务器、不需要绑信用卡**。
3. **（二选一）代码的一份拷贝**：点开本仓库页面，点右上角 **Fork（复刻）** 按钮把仓库复制一份到你自己的 GitHub 账号下——后面说的「你的仓库」都指这份 Fork；或者只在电脑上部署，去本仓库 **Releases（发行版）** 页下载最新部署包 zip。
4. **（可选）你自己的域名**：没有也行，Cloudflare 会免费送你一个 `你的项目名.pages.dev` 的网址，能直接用；有域名可以绑上，显得正规。域名在哪个平台买的都行，部署时按提示把解析指过来即可。

### 先分清两个地方（GitHub 和 Cloudflare 别搞混）

部署这件事要同时用两个网站，新手最容易栽在「这一步到底去哪个网站弄」。先看这张地图：

| 地方 | 里面的东西 | 干什么用（人话） |
| --- | --- | --- |
| **GitHub**（放代码的地方） | 仓库（Repository） | 存全部代码和数据文件的地方，本项目的一切源头都在这 |
| | Actions | GitHub 的「自动干活机器人」：按定时或你的指令，在云端把拉源、聚合、部署这一整套活干完，不用你的电脑开着 |
| | Releases（发行版） | 放打包好的 zip 给人下载的地方：部署包和校验文件都在这里拿 |
| | Secrets | 仓库的「保险柜」：存部署令牌这类不能公开的值，存进去谁也看不到原文 |
| **Cloudflare**（让项目跑起来的地方） | Pages | 站点就住在这里对外给人看。在控制台左侧 **Workers & Pages** 菜单里，点你的 Pages 项目（本项目叫 `ym-cfip`）管理它 |
| | Pages Functions | 站点的几个小接口（订阅、存快照、读快照）。它没有单独菜单——代码就在仓库 `functions/` 文件夹里，部署时跟着 Pages 一起生效，你不用单独管 |
| | KV | 云端小仓库，存访客保存的快照。在控制台 **Workers & Pages → KV** 菜单里建，在 Pages 项目的 **Settings（设置）→ Functions** 里以绑定名 `SNAP` 绑上 |

特别说明一句：本项目**不用** Cloudflare 的 Workers，也**不用** Cloudflare 的定时触发器——定时这件事在 GitHub Actions 那边（schedule），别去 CF 里找。

**两边怎么配合**：聚合和部署都在 **GitHub Actions** 里跑——机器人每约 2 小时把最新数据聚合好，再用 wrangler 把成品站点推到 **Cloudflare 的 Pages 项目**上对外给人看；访客在页面上存的快照，存在 **Cloudflare 的 KV** 里。一句话：**GitHub 是后厨（做菜和上菜的流程），Cloudflare 是店面（客人真正坐下来吃的地方）**。

几个词先混个脸熟，后面步骤里再遇到就不懵了：

- **Actions（读作「艾克申斯」）**：GitHub 提供的「自动干活机器」。你把要干的活写成一份说明书交给它，它就按时或按你的指令在云端自动执行，不用你的电脑开着。
- **工作流（Workflow）**：就是上面那份「说明书」本身，本项目的工作流文件是 `.github/workflows/update.yml`，名字叫「聚合优选 IP 数据」。
- **schedule（定时触发）**：工作流的一种启动方式，到点自动跑，本项目设的是约每 2 小时一轮。
- **dispatch（派发触发）**：工作流的另一种启动方式，人点一下按钮（或外部程序调用一下）就立刻跑一轮，不用等定时。
- **Secrets（仓库密钥）**：GitHub 仓库里的一个「保险箱」，专门存不能公开的值（比如部署令牌）。存进去之后谁也看不到原文，只能被工作流在运行时取用。
- **KV（键值存储）**：Cloudflare 提供的一个云端小仓库，按「名字 → 内容」存东西。本站的快照订阅就存在里面，绑定名（相当于给这个仓库起的门牌号）叫 `SNAP`。
- **wrangler（读作「兰格勒」）**：Cloudflare 官方的命令行工具，在电脑终端里敲命令用它把站点文件上传部署。

### 总共要花多少钱（结论：0 元）

把账算在前面，免得你部署到一半担心扣费：

- **Cloudflare 账号：免费。** 本项目只用 Pages（托管网页）和 KV（存快照）两样，免费版额度完全够用，不需要绑卡、不需要升级付费版。KV 每天写入有免费上限，本项目给快照做了全站封顶，不会因为访客乱点把额度刷爆（到了上限只是快照先存不了，清单照常更新）。
- **GitHub：免费。** 仓库保持**公开**，Actions 的定时任务对公开仓库免费、不限分钟；如果把仓库改成私有，定时任务会开始吃每月免费分钟数，超了会停跑——所以别把仓库设为私有。
- **域名：可选，唯一可能花钱的一项。** 不买域名就用 Cloudflare 送的 `你的项目名.pages.dev` 免费地址，一分钱不花；想要自己的域名才需要去注册商买，一年几十块钱，跟本项目无关、也不用在 Cloudflare 里买。

**一句话：按本文档部署，全程 0 元，唯一可选开支是自备域名。**

### 安全提醒（动手前先看完这一节）

- **CF API 令牌 = 你账号的钥匙，绝不能外泄。** 不要发给任何人，不要截图发到群里、论坛里求助（求助要截图，先把令牌和账号密码涂掉再发）；更不要把令牌写进代码文件里提交到仓库——公开仓库里的代码全世界都能看，令牌一旦提交等于把钥匙挂在了大门口，哪怕你随后删掉，别人也可能已经从提交历史里抄走了。令牌只有一个正当去处：仓库的 **Secrets**（填法见方式一）。
- **怀疑令牌已经泄露，别犹豫，立刻处理**：去 Cloudflare 把那把旧令牌删掉（删除即刻失效），再新建一把、把新值换进仓库 Secrets，然后手动 Run 一轮工作流确认部署步变绿——完整步骤见下方「出事了怎么办」里令牌那一条。
- **GitHub 和 Cloudflare 两个账号都开两步验证（2FA）。** GitHub：点头像 → **Settings** → **Password and authentication** → **Two-factor authentication** 按提示开；Cloudflare：点头像 → **My Profile（我的个人资料）** → **Authentication（身份验证）** 里开启。开启时给的恢复码抄下来存进密码管理器——这两个账号一个管代码、一个管站点，丢任何一个都很麻烦。
- **从别处 Fork 任何项目，先看一眼再开 Actions。** 本仓库的工作流只做聚合和部署，文件在 `.github/workflows/` 里，你可以自己打开看；养成习惯：Fork 不认识的仓库，先扫一眼它的工作流文件跑的是什么命令，再点启用，防的是有人在自动任务里塞私活。

## 方式一：全自动（Fork + 配 Secrets + 工作流自己跑）

**先说好坏（看完再决定要不要走这条）**

- ✅ 优势：配一次，终身自动——之后每约 2 小时自己拉源、聚合、部署，你连网页都不用打开；全程在 GitHub 和 Cloudflare 的云端跑，不用你自己的电脑开着；以后改了页面代码，也会随下一轮聚合自动上线。

### 【要用到的东西】

- 上一节准备的 GitHub 账号、Cloudflare 账号；
- 一份 Fork 到你名下的仓库（步骤 1 做）；
- 一个 Cloudflare **API 令牌**（相当于一把只给「部署 Pages」这一件事用的钥匙，步骤 3 现场创建）和你的 **Cloudflare 账号 ID**（一串在控制台里能复制到的字符，步骤 4 拿）——这两个值要存进仓库 Secrets（步骤 5）；

### 先把两个值说清楚（令牌是什么、丢了怎么办）

方式一全程只碰两个敏感值，逐个按「是什么 / 去哪拿 / 填到哪 / 干什么用 / 怎么保存、丢了怎么办」说清：

**① Cloudflare API 令牌（填进 `CLOUDFLARE_API_TOKEN` 的那串字符）**

1. **它是什么（人话）**：一把「只许干部署这一件事」的钥匙。工作流拿着它，就能以你的名义把站点文件推上 Cloudflare Pages；它不是你的账号密码，丢了也不会让人登进你的账号乱改别的东西。
2. **去哪儿建**：Cloudflare 控制台 → 右上角头像 → My Profile（我的个人资料）→ API Tokens（API 令牌）→ Create Token（创建令牌）→ Custom token（自定义令牌）→ 权限选 Account（账户）→ Cloudflare Pages → Edit（编辑）→ 创建。具体点位见下方步骤第 3 步。
3. **拿到后填到哪儿去用**：填进你 Fork 仓库的 Secrets，名字必须叫 `CLOUDFLARE_API_TOKEN`（点位见步骤第 5 步）。除了这一个地方，哪儿都不用填。
4. **它是干什么用的**：只在每轮工作流跑到「推送部署到 Cloudflare Pages」那一步时被取出来用一次，把聚合好的站点推上你的 Pages 项目。没有它，那一步会被自动跳过（数据照常聚合、提交，只是站点不更新）。
5. **要不要保存、丢了怎么办**：**要，而且必须当场存**——令牌创建成功后**只完整显示一次**，关掉那个页面就永远看不到了，所以一显示出来立刻点 Copy（复制），贴进你自己的密码管理器或一份只有你能看到的备忘里存好。填进 GitHub Secrets 后，**平时不用再看它**（Secrets 里的值谁都看不到原文，包括你自己）。**万一丢了**（忘了存、备忘丢了）：不用慌，回 Cloudflare → API Tokens 列表 → 把旧令牌那一行删掉（删除即作废）→ 按同样步骤重建一把新的 → 回 GitHub Secrets 把 `CLOUDFLARE_API_TOKEN` 的值更新成新令牌（点该行右边的编辑图标 → Update secret），下一轮工作流就恢复正常。**以后还会用到它的情况**：换 Cloudflare 账号部署、令牌被你手动删了、或怀疑令牌泄露时换新——都是「删旧建新再更新 Secret」这一套动作。

**② Cloudflare 账号 ID（填进 `CLOUDFLARE_ACCOUNT_ID` 的那串字符）**

1. **它是什么（人话）**：你 Cloudflare 账号的「门牌号」，告诉工作流「要部署到哪一个账号」——你可能有多个 CF 账号，靠它区分。
2. **去哪儿拿**：Cloudflare 控制台 → 点任意域名进概览页，右侧栏 **Account ID** 点复制；没有域名时在 Workers & Pages 页右侧也能看到。具体点位见步骤第 4 步。
3. **拿到后填到哪儿去用**：填进仓库 Secrets，名字必须叫 `CLOUDFLARE_ACCOUNT_ID`（点位见步骤第 5 步）。
4. **它是干什么用的**：和令牌配套，部署那一步靠它定位你的账号，再用令牌获得操作许可。
5. **要不要保存、丢了怎么办**：**它不是秘密**，不用特意保存——控制台首页/概览页随时能查到、抄回来，泄露了也没风险（光有门牌号没有钥匙进不了门）。填错的后果只是部署推到错的账号或报错，查对重填即可。

> 顺带把方式三里会碰到的授权说清：本地跑 `wrangler login` 时弹出的浏览器授权页，点 Allow（允许）后，登录凭据由 wrangler 自己存在你电脑的用户目录里，不用你记任何值；以后在这台电脑上部署不用重复登录。换电脑了重新 `wrangler login` 一次即可，没有「丢了」一说。

### 【常见问题】

- **工作流里「推送部署到 Cloudflare Pages」那步显示 skipped（跳过）？** 是 Secrets 没配或名字写错了——那步检测不到令牌就会自动跳过（聚合和数据提交不受影响）。回方式一第 5 步核对两个名字：`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`，一个字母都不能差。
- **部署那步报错说找不到项目（project not found）？** 是第 6 步建的项目名不是 `ym-cfip`。工作流按这个固定名字找项目，删掉重建同名项目，或者改 `.github/workflows/update.yml` 里 `--project-name` 后面的值跟你的项目名对上。
- **部署那步报 403 / 权限错误？** 令牌权限给错了。回 Cloudflare 按第 3 步重建一枚：权限那行必须是 Account（账户）→ Cloudflare Pages → Edit（编辑），建好把新令牌替换进 Secret。
- **想绑自己的域名？** Pages 项目页 → **Custom domains（自定义域）** → **Set up a custom domain（设置自定义域）** → 填你的域名 → 按页面提示去域名注册商那里加一条 CNAME 解析，指向它给你的 `ym-cfip.pages.dev` → 等状态变成 Active（生效）。做到这里你应该看到：用你的域名打开就是本站。

## 方式二：手动触发一轮（立刻更新数据）

适合：方式一已经配好，但你不想等下一轮定时，想现在就刷新一轮数据（或者某轮失败后要补一轮）。

**先说好坏**

- ✅ 优势：点几下、一分钟内就能让一轮新数据跑起来，不用等定时；不用终端、不用装任何东西，手机浏览器都能点；某轮失败后补救也靠它。
- ⚠️ 劣势：它只是「催一轮」，治标不治本——配置本身错了（比如令牌填错），触发多少轮都是红叉，还得回方式一去改；必须先配好方式一才能用，它自己不能独立部署；更新靠人记得去点，忘点就停在旧数据。

### 【要用到的东西】

- 一个已经按方式一配好的仓库（Actions 已启用）；
- 浏览器登录着你的 GitHub 账号。就这些，不用开电脑终端。

### 【步骤】

<details>
<summary>点开看详细步骤（照着点就行）</summary>

1. 打开你 Fork 的仓库页面 → 点顶部 **Actions**。
2. 看页面**左侧**的工作流列表，点「**聚合优选 IP 数据**」。
3. 页面右侧会出现一条蓝色横幅，右端有 **Run workflow（运行工作流）** 按钮，点它 → 弹出小框，**Branch（分支）保持 `main`** → 点里面绿色的 **Run workflow** 按钮确认。
4. 等几秒，**刷新一下页面**：运行记录列表最上面会出现新的一轮，标题前面是**黄色圆点**（表示正在跑）。一轮通常要跑几分钟（要逐个源拉取、验活）。
5. 等它变成 **绿色对勾 ✅** 就是成功了；变成 **红色叉号 ❌** 就是这轮失败了——点这一轮的**标题**进去，再看左侧/中间的步骤列表，**哪一步前面是红叉**就是坏在哪一步，点开那一步能展开日志，拉到日志最后几行看报错写了什么。

做到这里你应该看到：成功的话回到站点首页，「更新于」变成了刚刚的时间。

</details>

### 【部署完怎么验】

- 运行记录是绿勾，且站点首页「更新于」时间刷新 → 这一轮从聚合到部署全程通了。

### 【常见问题】

- **千万别在失败的那一轮上点 Re-run（重新运行）！** 失败的那一轮可能已经往仓库提交了一半数据，你点 Re-run，它会拿着旧状态硬往上推，容易在数据文件（`data/` 里的文件）上撞出**合并冲突（两份改动打架，谁也不让谁）**，越弄越乱。正确做法永远是：**按上面的步骤 Run workflow 触发一轮全新运行**，新一轮会从最新状态重新来，上一轮的烂摊子自动作废。
- **Run workflow 按钮找不到？** 多半是 Actions 还没启用（回方式一第 2 步），或者你停在了别的页面——确认你在仓库的 **Actions** 页、且左侧选中了「聚合优选 IP 数据」。
- **已经有一轮在跑，我又点了一次会怎样？** 不会打架：工作流设了排队串行，后触发的那轮会等前面跑完再开始，顶多是多等一轮的时间。
- **黄点转了十几分钟还不结束？** 偶尔某个源站很慢会拖住整轮，先等到 20 分钟；还不动可以点进那一轮 → 右上角 **Cancel workflow（取消运行）**，然后重新触发一轮新的。

## 方式三：本地 wrangler（应急 / 调试）

适合：全自动流程坏了、站点急着上线，或者你想在电脑上改改代码先本地部署看看效果。这一轮的数据和部署都在你电脑上完成，不经过 GitHub。

**先说好坏**

- ✅ 优势：全程在自己电脑上，出错日志就打在眼前，是三种里最好排查的；完全不依赖 GitHub，自动流程全坏了也能救急把站点推上线；改完代码立刻就能部署看效果，适合调试。
- ⚠️ 劣势：门槛最高——要装 Node.js 和 Python、要会开终端敲命令，新手最容易卡在这条；每轮聚合要在本地跑几分钟，电脑得全程开着；本地部署不改仓库，下一轮自动聚合会覆盖它，所以只适合应急和调试，不适合当长期更新方式。

### 【要用到的东西】

- 一台电脑（Windows / Mac / Linux 都行），能打开终端（Windows 用 PowerShell 或 CMD，Mac/Linux 用自带终端）；
- **Node.js**（wrangler 靠它运行）：去 [nodejs.org](https://nodejs.org) 下载 LTS（长期支持版）一路下一步装好；
- **Python 3**（聚合脚本靠它运行）：去 [python.org](https://www.python.org) 下载安装；Windows 安装时记得勾上「Add Python to PATH」；
- **代码一份**：去本仓库 **Releases（发行版）** 页下载最新部署包 zip 解压（里面是站点全部文件 + 当前一份数据），或者用 git 克隆仓库；
- 你的 Cloudflare 账号（部署时 wrangler 会弹浏览器让你登录授权）。

### 【步骤】

<details>
<summary>点开看详细步骤（照着敲就行）</summary>

1. 解压部署包（或克隆仓库），打开终端，`cd` 进入解压出来的文件夹（终端里输入 `cd ` 再把文件夹拖进终端窗口、回车，最省事）。
2. 先跑聚合，生成最新数据：在终端输入 `python scripts/aggregate.py` 回车（如果提示找不到 python，改敲 `python3 scripts/aggregate.py`）。它会逐个拉源、验活，跑几分钟是正常的，跑完文件夹里 `data/` 就是最新数据。
做到这里你应该看到：终端最后没有红色报错，`data/meta.json` 的修改时间是刚刚。
3. 把要部署的文件组装进一个 `dist` 文件夹（照抄工作流里的做法）：在当前文件夹里新建 `dist` 文件夹，再建 `dist/data`、`dist/functions` 两个子文件夹；把 `index.html`、`_headers` 复制进 `dist/`，把 `data/` 里的全部文件复制进 `dist/data/`，把 `functions/` 里的全部文件复制进 `dist/functions/`。
做到这里你应该看到：`dist` 里有 index.html、_headers 和两个子文件夹，结构和仓库根目录长得差不多。
4. 登录 Cloudflare：终端输入 `npx wrangler login` 回车 → 浏览器会自动打开 Cloudflare 授权页 → 点 **Allow（允许）** → 回到终端看到登录成功字样。
5. 部署：终端输入 `npx wrangler pages deploy dist --project-name ym-cfip` 回车（第一次会问是否创建项目，选 Yes；项目名必须是 `ym-cfip` 才和自动流程对得上）。等上传跑完，终端会输出一个部署地址。
做到这里你应该看到：打开输出的地址，站点已经是最新数据。

</details>

### 【部署完怎么验】

- 打开终端输出的部署地址（或你的正式域名），首页「更新于」是刚刚的时间 → 本地这一轮部署成功。

### 【常见问题】

- **敲 `npx wrangler` 说不是命令 / 找不到？** Node.js 没装好或终端是装之前开的——关掉终端重新开一个再试；还不行重装 Node.js 并确认安装时勾了加入 PATH。
- **本地部署会不会把自动流程弄乱？** 不会。本地这一轮只是把站点推上去，不改仓库；下一轮自动聚合会按时跑并覆盖成本轮最新数据，两边不冲突。
- **本地跑聚合特别慢？** 正常：它在逐个验证每个条目是否可用，源多就要等。只想快速看页面效果可以跳过第 2 步，直接用部署包里自带的那份数据组装部署。

## 探活（站点还活着吗：需要什么、怎么加、在哪看）

先分清两个容易混的东西：

- **本站对优选 IP 的「验活」是功能，不是运维探活**：聚合时探针逐个验证 IP 可不可用、访客在页面上点「本地检测」——那是给访客筛 IP 用的，跟「你的站点还活不活」没关系。
- **这一节说的是运维探活**：找一个外部的「巡逻员」，每隔一段时间访问一下你的站点，确认它还能打开、数据还在更新，挂了你能第一时间知道。

**需要什么**：一个能定时发请求的探活工具。本站作者用的是自己另一个项目 **ym-dash**（一个测活总览站，它的探活程序每 30 分钟把总览里的站点挨个请求一遍）；你没有 ym-dash 也没关系，任何能定时请求网址的 uptime（在线监测）服务都是一个道理，下面按 ym-dash 的加法写，换别的工具就是把同样的网址填进它那里。

**怎么加（在 ym-dash 里）**：

1. 打开 ym-dash → 登录它的后台 → 找到**站点管理** → 点**添加站点**；
2. **名称**填 `ym-cfip`（随便，好认就行），**URL** 填你的站点根地址（比如 `https://你的域名/` 或 `https://ym-cfip.pages.dev/`）；
3. 点**保存**，再点一次**立即检测**。
做到这里你应该看到：这一行显示状态正常、返回码 200、响应几百毫秒——探活加上了，之后每 30 分钟自动探一次，结果在 ym-dash 总览页直接看。

**探什么才算「真活」**（只探首页是不够的）：

- 首页返回 200 —— 只能说明静态页面还在，数据旧成什么样它不知道；
- 再打开 `https://你的域名/sub?regions=JP` ，能返回一串文本清单 —— 说明接口（Functions）也活着；
- 首页顶部「**更新于**」的时间在最近几小时内 —— 说明聚合 + 部署这条数据链也活着。三样都过，才算真活；哪一样挂了，去看下面「自动更新与自动任务」里对应的环节。

## 保活（需不需要定期弄点动静防休眠）

**结论：站点本身不需要保活。** Cloudflare 的 Pages / Workers 没有休眠机制，不需要你定期打开或发请求去「叫醒」它；绑的域名证书由 Cloudflare 自动续期，也不用管。需要人工偶尔盯的只有两件：

1. **GitHub 定时工作流别被平台停用**：GitHub 有个规则——公开仓库 **60 天没有任何活动**，它的定时工作流会被自动停用，数据就不再自动更新了。本项目的工作流自带一道保险：第 1 节说的每次聚合成功都会产生数据提交（本身就是活动），万一长期没数据变化，它还有一步「心跳保活」：距上次提交满 25 天时自动提交一个保活文件，让仓库保持活动。正常情况下你永远不用管；真被停用了也好办：打开仓库 → **Actions** 页 → 页面顶部会出现一条黄色提示说定时工作流已停用 → 点提示里的 **Enable workflow（启用工作流）** 按钮即可恢复。
2. **域名续费**：如果你绑了自己的域名，到期前记得在注册商那里续费——域名一过期，站点立刻打不开，这跟 Cloudflare 没关系，是域名本身没了。用免费的 `pages.dev` 地址则没有这回事。

## 自动更新与自动任务（部署者看这一张表就够）

| 什么在自动跑 | 谁触发 | 频率 | 在哪看 | 怎么手动触发 | 失败怎么办 |
| --- | --- | --- | --- | --- | --- |
| 拉源聚合 + 验活 + 生成数据 + wrangler 部署上线 | `update` 工作流（schedule 定时；原站另有外部调度器约每 100 分钟补一次 dispatch 派发） | 约每 2 小时一轮 | GitHub 仓库 → Actions →「聚合优选 IP 数据」的运行记录（绿勾/红叉） | Actions 页 → 选该工作流 → Run workflow（详见方式二） | **不要点 Re-run**（可能在数据文件上撞合并冲突），重新 Run workflow 开一轮新的；单个源失败当轮自动跳过、下一轮自动恢复，不用管 |
| 把新数据提交回仓库 | 同一工作流内（聚合有变化时） | 每轮 | 仓库首页的提交记录，提交信息带「data: 自动聚合」字样 | 跟着上一行一起，不用单独弄 | 同上，靠新一轮解决 |
| 心跳保活提交 | 同一工作流内 | 距上次提交 ≥ 25 天时才触发 | 提交记录里带「heartbeat: 保活定时任务」字样 | 不用手动 | 不用管，它只是防 GitHub 60 天停用规则的 |

**站点数据几小时没更新，先看哪里**：先打开仓库 **Actions** 页看最近一轮是不是**红叉**——是红叉就点进去看哪一步坏了（多半是某个源临时抽风，下一轮多半自愈；或部署步的令牌问题，按方式一常见问题对着查）；最近一轮是绿勾但站点没更新，多半是你看到的是缓存，强刷一次页面再看「更新于」。

## 出事了怎么办

东西用久了总有手滑删错、平台规则、过期失效的时候。这一节把每样东西出事的后果和重建办法写全，先看总表定性，再按条目找步骤。**先记一条总原则：这个项目里真正"原件"只有两样——各公开源发布的数据（在源站那里）和你的 CF / GitHub 账号本身；其余东西（数据文件、Pages 项目、快照索引）都是能重新生成的产物，删了大多能自己长回来。**

| 出事的东西 | 后果一句话 | 能不能重建 |
| --- | --- | --- |
| KV（`SNAP`）被删 / 解绑 | 快照功能停，站点和清单数据毫发无损 | ✅ 能，重新建好绑回 |
| `update` 工作流被 GitHub 停用 | 数据停在最后一轮，站点照常打开 | ✅ 能，Actions 页点一下启用 |
| 工作流连续红灯 | 数据不更新，站点用的是旧清单 | ✅ 按排查顺序走，多半自愈 |
| CF API 令牌被删 / 失效 | 新数据提交了却上不了线 | ✅ 删旧建新，换进 Secrets |
| Pages 项目被删 | 站点立刻下线 | ✅ 能，但域名和 KV 绑定要重绑 |
| 仓库 `data/` 数据文件损坏 / 误删 | 当轮清单可能异常 | ✅ 下一轮自动全量重新生成 |
| 域名过期 | 自定义地址打不开，`pages.dev` 地址没事 | ⚠️ 宽限期内续费可恢复；被抢注 = 永久丢失 |
| GitHub 仓库被删 | 自动更新停摆，站点还能照常开一阵 | ✅ 用发行包 zip 重建仓库 |

### 1. KV（`SNAP`）被删了 / 绑定被解开了

- **出事情形**：在 Cloudflare 控制台把 KV 命名空间删了，或者在 Pages 项目设置里把 `SNAP` 那行绑定删了（两种是不同的事，下面分别说）。
- **后果**：访客点「存快照」会报错，之前生成的 `/s/<id>` 快照链接打不开——**仅此而已**。站点首页、清单、`/sub` 订阅全都不受影响，因为清单数据在仓库的 `data/` 文件里，压根不经过 KV。
- **能不能重建**：能。
  - 只是**解绑**（命名空间还在）：数据还躺在原来的命名空间里。去 Pages 项目 → **Settings（设置）** → **Functions（函数）** → **KV namespace bindings** → **Add binding** → 变量名填 `SNAP` → 选回原来那个命名空间 → **Save** → 再手动 Run 一轮工作流让新部署带上绑定（点位全程见方式一第 7 步）。绑回来之后，旧快照链接全部原样恢复。
  - **命名空间被删**：里面的快照内容跟着一起没了，找不回来。但不用慌：快照是「内容定址」的——同一份清单算出同一条链接，谁把同一份清单重新点一次「存快照」，生成的新链接和原来那条一模一样，等于自动找回。按方式一第 7 步新建一个命名空间、绑回 `SNAP` 即可，下一轮工作流跑完新快照就能正常存了。
- **影响范围**：只有快照功能，且多数能自愈，别因为这个去动其他设置。

### 2. update 工作流被 GitHub 停用了（60 天无活动规则）

- **出事情形**：仓库长期没有任何活动，GitHub 按规则自动停用了定时工作流；或者你（或协作者）在 Actions 页手动把它 Disable 了。
- **后果**：不再有新一轮聚合。站点照常打开、`/sub` 照常返回，只是数据停在最后一轮，首页「更新于」的时间不再往前走——**不会报错、不会变空**，是"静悄悄地变旧"。
- **能不能重建**：能，一分钟的事。
  1. 打开你的仓库 → 点顶部 **Actions**；
  2. 如果页面顶部有一条黄色提示说定时工作流已被停用，点提示里的 **Enable workflow（启用工作流）**；没有黄条的话，点左侧工作流列表里的「聚合优选 IP 数据」→ 点页面右上角的 **···** → **Enable workflow**；
  3. 启用完别干等：按方式二手动 **Run workflow** 跑一轮，看到绿勾、站点「更新于」变成刚刚，确认链条真的活了。
- **影响范围**：只有自动更新这一件事。怎么预防它再次发生，「保活」一节已经写了（工作流自带 25 天心跳保活，正常情况根本轮不到被停用）。

### 3. 工作流连续红灯（跑一轮挂一轮）

- **出事情形**：Actions 里最近几轮全是红叉，数据好几天没更新。
- **后果**：和上一条一样，站点用旧清单照常服务，访客基本无感；你慌也没用，先定位是哪一步红。
- **排查顺序（照这个顺序，别乱点）**：
  1. 点进**最新一轮带红叉**的运行 → 展开失败的那一步，看它叫什么名字；
  2. **拉源 / 聚合步红**：多半是上游源集体抽风或改了格式。先什么都不做，等下一轮——单个源失败工作流本来就会自动跳过。如果**连红三轮以上**，再去「常见问题」看怎么改源列表 / 加自己的源；
  3. **提交（推送数据）步红**：多半是冲突或权限问题。记住老规矩：**永远不要在失败的那一轮上点 Re-run**，原因和正确做法（开一轮全新的 Run workflow）方式二的常见问题里已经写透了，这里不重复；
  4. **部署步红**：那不是聚合的问题，是令牌或账号 ID 的问题，直接跳到本节第 4 条处理。
- **一个定心丸**：就算某一轮抓回来的数据多源全挂、条数暴跌，工作流里有**骤降保护（熔断）**——它会把这一轮的新数据冻结不用，站点继续用上一轮的好数据。所以红灯最坏的结果也只是"数据旧一点"，**不会出现站点变空、清单清零**。
- **影响范围**：只有数据新鲜度。

### 4. CF API 令牌被删了 / 失效了

- **出事情形**：你在 CF 那边把令牌删了、令牌被平台作废，或者 Secrets 里当初就填错了值。
- **后果**：聚合照常跑、数据照常提交回仓库，但**最后一步部署会报错**（日志里多是 401 / 403 字样），新数据上不了线。典型症状：仓库首页能看到新的「data: 自动聚合」提交，站点「更新于」却纹丝不动。
- **能不能重建**：能，令牌本来就是消耗品，换一把是常规操作。
  1. 回 Cloudflare 重新建一把令牌（建的点位、权限、"只显示一次必须当场复制"这些，方式一的「先把两个值说清楚」一节已经五点写全，照着做）；
  2. 打开仓库 → **Settings** → **Secrets and variables** → **Actions** → 点 `CLOUDFLARE_API_TOKEN` 那一行 → **Update（更新）** → 把新令牌粘进去 → 保存；
  3. 顺手把 CF 那边那把旧令牌删掉（如果只是失效还没删的话），免得留一把废钥匙在门上；
  4. 手动 **Run workflow** 跑一轮，看到部署步变绿、站点「更新于」刷新，处理完毕。
- **影响范围**：只有"上线"这最后一公里；恢复前站点用旧数据照常服务。

### 5. Pages 项目被删了

- **出事情形**：在 Cloudflare 控制台把 Pages 项目 `ym-cfip` 删了（或手滑删错了项目）。
- **后果**：站点**立刻下线**，`pages.dev` 地址和绑的自定义域名都打不开。但东西没全没：仓库和 `data/` 数据在 GitHub 那边完好；KV 命名空间是账号级的独立资源，**不会跟着项目一起被删**，快照内容还在里面。
- **能不能重建**：能，但有两样项目级设置要手动重绑（见第 3、4 步，别漏）。
  1. 打开仓库 → **Actions** → 手动 **Run workflow** 跑一轮 `update`：它的部署步是用 wrangler 按项目名 `ym-cfip` 直推的，**项目不存在时会自动新建一个同名项目**，这一轮跑完站点就回来了（实在等不及，也可以用方式三在电脑上本地 wrangler 先顶上）；
  2. 回 Cloudflare 控制台确认 `ym-cfip` 项目已经重新出现、部署记录里有最新一轮；
  3. **重绑 KV**：项目重建后绑定是空的——进项目 → **Settings** → **Functions** → **KV namespace bindings** → 变量名 `SNAP` → 选**原来那个**命名空间（数据都在，别新建）→ **Save**；
  4. **重绑自定义域名**（如果你原来绑了的话）：进项目 → **Custom domains（自定义域）** → 重新添加你的域名，按提示走完；
  5. 再手动 Run 一轮工作流让绑定生效，然后打开站点验证：首页能开、「更新于」是新的、随便存一份快照能生成链接——三样都过才算完全恢复。
- **影响范围**：下线时间 = 你发现并处理的速度；数据零损失。

### 6. 仓库里 data/ 数据文件损坏了 / 被误删了

- **出事情形**：手动改文件时把 `data/` 里的清单文件改坏了，或者误删了其中几个。
- **后果**：最坏就是当前这一份清单内容异常（比如某个地区打开是空的）。
- **能不能重建**：能，而且**基本不用你动手**——`data/` 是每一轮聚合从零重建的产物，不是什么唯一原件：手动 **Run workflow** 跑一轮新的，它会把全部数据文件重新生成并覆盖，坏文件自动被好文件顶掉。
- **唯一的例外**：手写的种子文件 `seed-usjp.txt`（你自己加的静态条目）不在每轮自动生成的范围里，它要是被删了，按这个点位找回：打开仓库 → 点开这个文件的页面（删了就去仓库首页的提交记录里找删除前那次提交）→ 点 **History（历史记录）** → 打开删除之前的那一版 → 复制内容 → 重新新建同名文件粘回去提交；懒得翻历史的话，Releases 页下载最新版发行包 zip，里面有同一份文件，拷回来即可。
- **影响范围**：一轮之内自愈，不用慌，更不要因为这个去重装、重 Fork。

### 7. 域名过期了

- **出事情形**：你绑的自备域名到了期没续费。
- **后果**：**只有那个自定义域名打不开**；Cloudflare 送的 `你的项目名.pages.dev` 地址不受影响、照常打开，聚合和更新也照常跑——站点没死，只是"正门"关了、"侧门"还开着。
- **能不能重建**：分两种情况——
  - **还在宽限期内**（大多数注册商过期后有几十天宽限期）：赶紧在注册商那里续费。续上之后什么都不用改：域名的解析记录都还在 Cloudflare 这边，域名一恢复，站点自动跟着恢复。
  - **已经掉出宽限期、被别人抢注了**：这个域名永久拿不回来了（**这是本节里唯一真正不可逆的情况**）。只能换一个新域名：新域名接入 Cloudflare → 在 Pages 项目的 **Custom domains** 里绑上 → 把你写在各处（客户端订阅备注、分享给别人的地址）的旧地址换成新的。
- **影响范围**：只影响用旧域名访问的人；提前在注册商那里开自动续费，就不会走到这一步。

### 8. GitHub 仓库被删了

- **出事情形**：仓库被误删，或账号出问题导致仓库没了。
- **后果**：代码、提交历史和自动更新一起停摆；但**已经部署到 Cloudflare 上的成品不受影响**——Pages 项目、KV 快照都在 CF 那边，站点会停在最后一版继续服务一阵子，只是数据不再更新。
- **能不能重建**：能，靠发行包。
  1. 在 GitHub 新建一个同名空仓库（名字还叫 `ym-cfip`，省得各处地址要改）；
  2. 去原仓库的 **Releases** 页——仓库没了 Release 也进不去，所以这一步靠你**平时存好的发行包 zip**（或者从你 Fork 过的副本、本地备份里拿同一套文件）：把 zip 解压后的全部文件上传 / 推送到新仓库；
  3. **重新配 Secrets**：仓库被删时，里面存的 `CLOUDFLARE_API_TOKEN` 和账号 ID 跟着一起没了，不会自己回来——按方式一重新填一遍（令牌如果也找不到了，先去 CF 删旧建新）；
  4. 到 **Actions** 页启用工作流，手动 **Run workflow** 跑一轮：部署步会按项目名对接回 CF 上原来那个 Pages 项目，数据链从这一轮起恢复；
  5. 提交历史回不来了，但那只是"账本"，不影响使用。
- **影响范围**：恢复前数据不更新；给你一个习惯建议——**每个大版本把 Releases 里的发行包 zip 下载一份存到手机或网盘**，这就是本条的保命符。

## 订阅端点 /sub

把选项写进链接，客户端拉取时现算。示例：

```
/sub?regions=JP,US&n=20&ms=200&ui=12
```

| 参数 | 说明 |
|---|---|
| `regions` | 地区代码逗号分隔，缺省 `JP,US` |
| `n` | 每个地区最多 N 个 |
| `rn` | 单独定量，如 `rn=JP.10,US.5`（覆盖 `n`） |
| `ms` | 最大延迟 ms（按源标注延迟） |
| `mbps` | 最低速度 Mbps（按源标注速度） |
| `carrier` | 运营商可多选（逗号分隔，如 `移动,电信`）：带标注的只留所选，无标注源保留 |
| `ports` | `443` 或 `tls`（443/8443/2053/2083/2087/2096），缺省全部 |
| `mode` | `random` 随机抽取，缺省质量优先（源序） |
| `stack` | `stack=6` 输出 IPv6 池（此时 regions/ms/mbps 不适用，可用 `n` / `carrier`） |
| `group` | 数据分组 `best`（高速优选）/ `full`（全部可用）/ `extra`（全国补充）/ `sw`（三网专区）/ `all`（合并总表，缺省），与页面分组一一对应 |
| `ui` | 建议客户端更新间隔（小时），写入 `profile-update-interval` 响应头 |
| `fmt` | 导出格式模板（URL 编码），变量 `{地区} {代码} {序号} {延迟} {网速} {运营商} {来源} {端口} {日期} {标签} {旗帜}` 自由组合；缺省为 `#代码序号 [原始标签]` |

参数写错会直接返回 400 并注明哪个参数不合法（如 `ms=abc`、`ports` 不在枚举内、`n`/`rn` 为负），不再静默忽略或悄悄给空结果。

页面上的「我的订阅链接」卡会随选项自动拼好这条链接，复制即用。

## 数据自动聚合（总池为什么是活数）

- GitHub Actions 默认**每 2 小时**运行 `scripts/aggregate.py`：抓取全部源 → 解析（原生格式源直接收录；混杂格式源提取地区代码，识别不了一律剔除）→ 去重 → 生成 `data/*.txt` 与 `data/meta.json`，有变化才提交，Pages 随之自动重新部署。
- **每轮从零重建、不是往旧池子上叠加**：源增它增、源减它减，同一 IP:端口 被多个源收录只算一次（按来源优先级归属）。所以总池数字每轮都会小幅浮动，这是正常现象，不是统计错误。
- **单源故障不冲池、但也不无限续命**：某个源某轮抓取失败/为空时，先沿用它上一轮的数据（页面「来源」与页眉会如实标注该源未恢复、不是正常状态），连续 6 轮（约 12 小时）都失败就停用沿用；任一池单轮跌幅超 20% 时先冻结一轮不发布，连续两轮仍跌则判定上游缩水已成常态、按新数据发布并告警——既防单轮事故发空池，也不会把数据永久冻在旧值。
- **改频率**：编辑 `.github/workflows/update.yml` 的 cron 一行即可（默认 `20 */2 * * *` = 每 2 小时；GitHub 定时任务最密 5 分钟一次）。这是部署者自己的设置，每份部署互不影响。
- `data/history.json` 保留最近 30 次聚合的条数记录，页面底部可查。
- 静态种子数据 `seed-usjp.txt`（美日精选）不随源更新，可自行编辑增删。

## 数量与拉取方法（为什么每个地区只有几十到几百条）

先给数字：总池一千余条、六十多个地区，其中美国三百多条、日本一百多条、新加坡、香港各几十条，往后多数地区只有几到几十条，小地区可能只有 1–2 条（每轮浮动，实时数字以页面「数据来源」与地区墙为准）。别家动辄「每地区几千条」，差别来自**拉取方法**，不是谁漏抓了：

**本站的方法：只收别人实测后发布的成品清单，再严过滤。**
1. **不自己扫网段**：27 个 IP 源都是维护者在各自网络里实测后发布的优选清单，单个源本来就只有几十到几百条。本站只拉取、解析、合并，不对 Cloudflare 官方网段做扫描。
2. **无地区标注一律剔除**：混杂格式的源必须能识别出地区代码才收（识别不了直接丢），宁缺毋滥 — 这一刀就砍掉不少。
3. **按「IP:端口」全网去重**：同一个 IP 被 5 个源同时收录，在总池里只算 1 条（按来源优先级归属）；同 IP 的重复条目不重复计数。
4. **每轮从零重建**：不攒历史库存，源站剔除的失效条目本站同步消失；源站整轮抓取失败时先沿用其上一轮数据（会在来源页标注），连续 6 轮失败才停用。

**别家「几千条一个地区」通常是另一种做法：**
- **扫描型**：拿官方 CIDR 段（约 150 万地址）批量扫，产出的是「扫到的地址」而非「测好的优选」，绝大多数没测过速度、很多是死的 — 本站把这种数据单独放在 ⑥「大池采样」里并标注未实测，不混进主池充数。
- **采集型**：把几十个源无差别堆叠，不验地区、不去重、失效不删，数字大但水分大。

**取舍很明确**：本站主池走「条条有出处、有地区、去过重」的口径，数量自然小一个量级；想要量，用 ⑥ 大池采样（官方段随机采样 + 本地检测自己筛）。地区分布则由源决定 — 源多从国内测美/日/新/港，小地区只有零星覆盖，这是全行业的共同现状。

**关于「已聚合 0 条」与三网专区**：源站会改格式或出故障。已实测到的情况（2026-11-06）：CFYes、麒麟等源改为按运营商分文件、行内不再带地区标注 — 这类「无地区、但有运营商实测」的条目本站破例收进**三网专区**（代号 SW，选地区时可像地区一样勾选，与总池同地址时以地区版为准）；CM 优选 2 的文件一度混入网页代码（其生成器故障），非法行被解析器自动剔除、有效行正常收录，全源无有效行时整源跳过并注明。聚合脚本会识别这些情况并在页面「数据来源」里逐源注明，源站恢复后下一轮自动回归 — 不是本站漏抓，也不会拿脏数据充数。页面每个源下方还标有本轮拉取条数、源站更新节奏与本站抓取时间，可自行对账。

## 口径与边界

- **标注数据不是你的实测**：延迟/速度是源在其测试地的成绩。离测试地越近参考价值越高；你本地的真实表现以「检测本地可用 / 本地测速」和本地 CloudflareSpeedTest 为准。
- **「本地可用」定义**：浏览器向 IP 发起 HTTPS 握手，超时内有响应即记可用（证书不匹配 IP 会报错返回，测的是报错前耗时）。可用 ≠ 节点能用或速度达标。开着代理时测的是经代理的连通性。
- **广电**：全网暂无公开的广电实测优选源。选广电时返回通用条目并给出提示 — 广电用户请用本地检测在自家网络实测筛选。
- **三网专区（SW）**：少数源只按运营商实测、不标地区，其条目以代号 SW 收录（备注带运营商与源站测速），可像地区一样勾选、进订阅（`regions=SW`）；它只有运营商口径、没有地区，旗帜变量对它留空。不勾就不出现在任何默认清单里。
- **格式自适应（尽力而为）**：聚合对宽松格式源按「标准 → Base64 解码 → 分享链接 → 兼容扫描」顺序自动适配，源站小改版一般不用改代码；用兼容解析接管时会在该源备注里标明。仍救不了的只有源站把数据加密、需登录或改用网页动态渲染的情况 — 那种源会在来源里显示收录为 0 并注明无法识别。
- **实时订阅不含本地可用**：本地检测只存在于访客浏览器，服务端无法复现，故 `/sub` 只接受地区/数量/门槛/运营商/端口/格式参数。要把本地测通结果变成订阅，用③卡的**快照订阅**：把当前清单定格存进 KV，链接内容就是你测过的那批。
- **探测超时统一 5 秒**：全池检测、清单测速、IPv6 与大池探测都用 5s（对齐 Mihomo/Clash 健康检查的业界默认），避免同一条目在这处通、在那处超时。
- **计数对得上账**：检测数与生成数不一致通常是运营商/门槛过滤在起作用（检测不分运营商、生成会过滤），页面会把被滤掉的条数明确标注；导出默认按地区分组编号（日本 1..N 完再到美国），与 `/sub` 口径一致。
- **优选域名**由第三方维护，使用人数多时晚高峰可能变卡，适合作回退入口。域名池每轮聚合时做 DNS 解析筛除（解析不通的直接剔除，筛除数记在 meta 与直链备注里）；但「能解析」不等于「在你网络上快」，最终以页面「批量实测」为准。

## Fork 部署与原站的区别（为什么一开始没有自动更新）

代码与原站一模一样，自动更新的能力全在工作流里；Fork 后暂时用不上，是 GitHub 的安全规则让「现成配置」不能跟着 Fork 走：

1. **Secrets 不复制**：原仓库的部署令牌、账号 ID 不会跟到 Fork。走令牌直推部署的，要在自己 Fork 的 Settings → Secrets 里配 `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`（只用 Git 连接部署的可跳过，没配时推送步骤会自动略过；已配令牌时每轮聚合都会把仓库最新页面一并推送部署，改了页面代码也会随下一轮聚合自动上线）。这条路线的完整配法见上方[方式一：全自动](#方式一全自动fork--配-secrets--工作流自己跑)。
2. **Actions 默认关闭、定时任务默认不跑**：Fork 后必须去仓库 **Actions** 页手动启用 `聚合优选 IP 数据` 工作流一次，它才会每 2 小时自动聚合——这是「不自动更新」的头号原因。
3. **60 天规则**：公开仓库 60 天无活动，定时工作流会被 GitHub 自动停用；本工作流带心跳保活步，正常聚合的提交也不会让它触发，长期关停后回来重新启用即可。
4. **云端资源自己建**：快照订阅用的 KV 命名空间在部署者自己的 Cloudflare 账号里，Pages 绑定变量名必须为 `SNAP`。
5. **上游更新不自动流入**：原仓库发新版，在 Fork 页点 **Sync fork** 手动同步（只带代码，不动你的数据与配置）。

补齐「启用 Actions +（令牌路线的）两个 Secrets + 绑 KV」后，Fork 的更新节奏与内容与原站完全一致（38 个数据源全是公开地址）。原站与 Fork 的实际差别只剩：原站配置已由作者配好、另有作者自己的日常巡检在盯；其余平级。

## 故障检查与维修

- **先看站内**：页面顶部「更新于」时间 + 「来源」类目逐源条数/抓取时间——时间新、条数正常，数据链就是好的。
- **再看工作流**：仓库 Actions → `聚合优选 IP 数据` 最近一次是否绿勾；红了点进去看失败步骤（单源失败当轮自动跳过，部署步失败多是令牌/账号 ID 问题）。
- **再看部署**：Cloudflare 后台 Pages 项目的部署记录。清单不更新、「更新于」不动，九成是工作流没启用或被 60 天规则停用。
- 快照存不了先查 KV 绑定变量名是否为 `SNAP`；订阅内容不对先对「订阅端点 /sub」参数表；其余现象见下方「常见问题」。

## 常见问题

**Q：为什么某个源显示「已聚合 0 条」？**
A：该源当轮条目与别的源重复、或没有可识别的地区标注（按「宁缺毋滥」规则剔除），没有净增条目，属正常现象，不代表源挂了。

**Q：总池条数为什么每轮都不一样？**
A：每轮聚合都把全部源重新抓一遍、从零重建：源增它增、源减它减、重复只算一次。浮动是个位数到几十条的正常呼吸，页面顶部「更新于」是最近一轮的时间。

**Q：检测了 301 个，生成清单只有 295 个，差在哪？**
A：检测只看通不通、不分运营商；生成时会执行运营商/延迟/速度/端口过滤。多半是运营商筛选滤掉了别家运营商的标注条目 — 页面计数旁会标注「运营商筛选滤掉 N 条」，对得上账。

**Q：为什么每个地区条数比别家少那么多？**
A：拉取方法不同。本站只收各源实测发布的成品清单，且无地区标注剔除、按 IP:端口 全网去重、每轮重建不攒库存；别家的「几千条」多是扫描官方网段的未实测地址或未去重的采集堆叠。详见上方「数量与拉取方法」一节；想要量可用页面 ⑥「大池采样」。

**Q：聚合频率能改吗？**
A：能。改 `.github/workflows/update.yml` 里 cron 一行（默认每 2 小时）。注意它和页面上「客户端更新间隔」是两回事：后者只是写给客户端的拉取建议（`ui` 参数），不改变后台聚合节奏。

**Q：订阅链接里的内容多久变一次？**
A：链接本身实时现算，内容取决于数据新鲜度：聚合每 2 小时更新一次（可改），客户端按 `ui` 建议间隔或其自身设置拉取。

**Q：部署后 Actions 不跑？**
A：Fork 的仓库默认禁用 Actions，到仓库 Actions 页手动启用；另外定时任务在 GitHub 免费版偶有延迟，属正常。

**Q：可以加自己的源或自己的 IP 吗？**
A：可以。编辑 `seed-usjp.txt` 加静态条目；或改 `scripts/aggregate.py` 的源列表加新源（需能解析出地区）。

**Q：新 Cloudflare 账号点「连接 GitHub」一直跳回应用设置页，看不到仓库？**
A：GitHub 上的「Cloudflare Workers and Pages」应用只能绑定一个 Cloudflare 账号。若你的 GitHub 已绑过另一个 CF 账号，新账号就连不上（卸载重装会断开旧账号项目的 Git 部署，慎重）。解法是走**令牌直推**：完整步骤已整合到上方[方式一：全自动](#方式一全自动fork--配-secrets--工作流自己跑)（先直传建一个名为 `ym-cfip` 的项目，再配两个 Secrets），照着做即可，这里不再重复。

**Q：Fork 后工作流里「推送部署」那步需要我处理吗？**
A：不需要。没配上述两个 Secrets 时该步自动跳过，聚合与数据提交照常；连 Git 部署的用户本来也用不到它。

## 隐私

- 本站无统计、无账号；页面与数据文件是静态托管，另有三个轻量后端端点（Pages Functions）：`/sub` 实时订阅、`/save` + `/s/<id>` 快照存取（用 KV 存快照内容）。
- 访客属地识别由访客浏览器直接向第三方 IP 库（ipwho.is / freeipapi / ipapi.is 等）查询自己的出口 IP 后在本地显示——查询请求会把访客的出口 IP 发给这些第三方（这是属地识别的必要代价），结果不回传本站、不存储。
- 保存快照时，为防滥用刷爆 KV 写额度，服务器会在 KV 里短暂记录来源 IP 的保存计数（2 天自动过期），此外不记录访客信息。
- 页面设置（复检站点、聚合间隔备忘、分享配置）只存访客浏览器 localStorage / URL。

## 📦 部署包 · 优缺点 · 已知问题（速览）

### 部署方法

完整部署步骤看上方「新手先看这里」到「方式三」四节（全自动 / 手动触发 / 本地 wrangler 三种方式，每一步都写明了去哪个页面、点哪个按钮、做完应该看到什么）。一句话概括：**推荐 Fork 后开自动流程**——仓库自带的 GitHub Actions 流程会定时拉取、聚合、去重并自动部署上线，配好后基本不用管；发行版 zip 只在本地应急部署时用（Releases 页下载，附 `SHA256SUMS.txt` 校验）。部署包只含程序和当前一份清单快照；你客户端里填的订阅地址、节点设置都不受重新部署影响。

### 优点

- 清单是「活」的：多来源自动聚合，每两小时左右刷新一轮，不用手动到处找优选 IP。
- 按地区和 IPv4/IPv6 分类整理，数量、更新时间都标清楚，心里有数。
- 提供 /sub 订阅端点，地址填进客户端就能定时自动同步最新清单。
- 做了去重和地区修正，不是把来源原样堆在一起。

### 缺点 / 要花钱的地方

- 完全免费，0 元；不需要服务器，可选成本只有自备域名。
- 数据来自公开来源的聚合：总量和质量会随来源波动，某个地区偶尔变少是正常现象。
- 优选 IP 只是「相对更优」的候选清单，不保证每一个在你的网络下都是最快，最终速度取决于你本地运营商和时段。

### 和同类有什么不同

- 网上流传的优选清单多是某人某天测完的一次性文件，过期没人管；这份是流水线作业：自动拉取、聚合、去重、修正、发布，全程不用人盯着。
- 清单和订阅端点是一体的：网页能看、客户端能订，不用自己再加工格式。

### 已知问题 / 注意事项

- 自动更新走 GitHub 定时调度，偶尔会延迟，清单时间差一两个小时属正常。
- 同一个 IP 在不同地区、不同运营商下表现差异很大，建议优先选自己所在地区的分组，并以实测为准。
- 免费 CDN 节点策略由 Cloudflare 决定，个别 IP 可能被限速或不可用，换同组其他 IP 即可。
